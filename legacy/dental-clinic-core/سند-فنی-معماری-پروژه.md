## ۲. الگوی امن صفحات — مهم‌ترین درسی که یاد گرفتیم

**مشکل:** روی این نصب وردپرس خاص، صفحه‌های جدید که با `add_submenu_page` به‌صورت مستقل ثبت می‌شدن، گاهی با خطای مرموز «شما اجازه‌ی دسترسی ندارید» یا صفحه‌ی سفید مواجه می‌شدن — علتش هیچ‌وقت ۱۰۰٪ کشف نشد، ولی الگوی زیر همیشه جواب داد:

> **همه‌ی صفحه‌های جدید، به‌جای صفحه‌ی مستقل، از طریق پارامتر روی صفحه‌ی `dental-dashboard` (که از اول تضمین‌شده کار می‌کنه) رد می‌شن.**

```php
// ثبت منو — لینک مستقیم، بدون callback جدا
add_submenu_page('dental-dashboard', 'انبار', 'انبار', $staff_cap,
    'admin.php?page=dental-dashboard&inv_view=hub');
```

```php
// داخل خودِ render_dashboard() — نه با هوک admin_init زودهنگام!
public function render_dashboard(): void {
    if (isset($_GET['inv_view'])) {
        // چک دسترسی...
        (new Dental_Page_Inventory_Hub())->render();
        return; // نه exit — چون باید داخل چارچوب عادی پیشخوان بمونه
    }
    // ادامه‌ی رندر عادی داشبورد...
}
```

⚠️ **نکته‌ی حیاتی:** این چک باید **داخل خودِ متد رندر عادی** باشه، نه با یه هوک `admin_init` زودهنگام که `exit` می‌زنه — چون اون‌جوری هیچ‌وقت فرصت نمی‌شه CSS/JS پیشخوان لود بشه و صفحه کاملاً بدون استایل («سفید») درمیاد. این خودش یه بار اتفاق افتاد و باگ بزرگی بود.

### الگوی پرینت (خروجی مستقل، بدون چارچوب پیشخوان)
همون الگو، ولی به‌جای `return`، `exit` می‌زنه و کل `<html>` رو خودش می‌سازه:
```php
public function maybe_print_shift_week(): void {
    if (!isset($_GET['page']) || $_GET['page'] !== 'dental-dashboard' || !isset($_GET['print_shift_week'])) return;
    // چک دسترسی...
    (new Dental_Page_Shift_Weekly())->render_print($jy, $jm);
    exit;
}
```

### `remove_submenu_page` — با احتیاط
این تابع هم یه‌بار باعث خرابی صفحاتی شد که قبلاً کاملاً سالم بودن. **توصیه: ازش استفاده نکن**، مگر مجبور باشی. برای گروه‌بندی بصری منو، به‌جاش از **چیدمان پشت‌سرهم + پیشوند مشترک در اسم** استفاده کن (مثلاً «💰 مالی: دفتر روزانه»).

## ۳. Permission — قانون طلایی

**هیچ‌وقت** به یه capability رشته‌ای سفارشی (مثل `dental_manage_all`) که ممکنه فراموش بشه به نقشی داده بشه، تکیه نکن. دلیل: یه‌بار این دقیقاً همین اتفاق افتاد و کلی صفحه برای «مدیر کلینیک» (نقش سفارشی، نه ادمین واقعی وردپرس) قفل موند.

**قانون فعلی:**
- همه‌ی منوها با یه capability واحد و مطمئن ثبت می‌شن: `dental_manage_reception` (که به هر ۵ نقش کارمند داده شده)
- کنترل واقعی «کی حق دیدن محتوا رو داره» **داخل خودِ صفحه**، با این تابع کمکی انجام می‌شه:
```php
private function user_has_role(array $allowed_roles): bool {
    if (current_user_can('manage_options')) return true;
    $cu = wp_get_current_user();
    return !empty(array_intersect((array)$cu->roles, $allowed_roles));
}
// استفاده:
if (!$this->user_has_role(['dental_admin','dental_financial'])) wp_die('...');
```

نقش‌های موجود: `dental_admin` (مدیر کلینیک)، `dental_doctor`، `dental_secretary`، `dental_financial`، `dental_assistant`. کاربر می‌تونه چند نقش هم‌زمان داشته باشه (فیلد `_dental_active_role` تعیین می‌کنه با کدوم نقش وارد شده).

## ۴. نکات فنی دیگه که باگ ساختن و رفع شدن

| مشکل | رفع |
|---|---|
| `dbDelta()` قابل‌اعتماد نیست برای اضافه‌کردن ستون به جدول موجود | `fix_missing_columns()` صریح + پرچم خودترمیم (`admin_init`، یک‌بار) |
| `window.open(url, '_blank')` باعث استفاده مجدد از تب قدیمی می‌شه | همیشه `window.open(url, 'dental_print_' + Date.now())` |
| `esc_url()` توی جاوااسکریپت، `&` رو به `&amp;` تبدیل می‌کنه | `String.fromCharCode(38)` یا `esc_url_raw()` |
| nonce تولیدشده بلافاصله بعد `wp_signon()` نامعتبره | باید صریح `wp_set_current_user($user->ID)` بعد signon و قبل ساخت فرم بعدی صدا زده بشه |
| `check_admin_referer()` روی صفحات frontend (نه wp-admin) بی‌ثباته | برای صفحات frontend از `wp_verify_nonce()` مستقیم استفاده کن |
| زمان محلی vs UTC | همیشه `current_time('timestamp')` یا `current_time('mysql')`، نه `time()` خام |
| رندر همه‌ی ردیف‌های یه جدول بزرگ (۱۰۰۰+ ردیف) با فیلتر جاوااسکریپتی سمت مرورگر | برای جدول‌های بزرگ همیشه فیلتر/صفحه‌بندی **سمت سرور** (کوئری با `LIMIT`/`OFFSET` و `WHERE`)، نه رندر همه و مخفی‌کردن با CSS |
| ایموجی توی heading فایل Word (docx) باعث به‌هم‌ریختن ترتیب متن راست‌به‌چپ می‌شه | ایموجی رو فقط توی بدنه/جدول بذار، نه توی عنوان‌های اصلی سند |

## ۵. لیست کامل ماژول‌ها (تا نسخه ۲.۴.۰)

- **بیماران و پرونده** — چارت دندانی، تاریخچه، خلاصه پرونده
- **کاتالوگ خدمات** — ۳۸۸ خدمت قیمت‌گذاری‌شده، درختی، جستجوپذیر
- **پذیرش و پرونده روزانه پزشک**
- **مالی** (گروه‌شده در سایدبار): مالی و اقساط، دفتر روزانه، گزارش درآمد و عملکرد (با پرینت)
- **شیفت‌بندی اتاق‌ها**: تنظیمات اتاق، برنامه ماهانه دکتر/دستیار (با چیدمان خودکار + قفل)، برنامه هفتگی (با هشدار تداخل)
- **انبار**: کالاها (۱۱۴۵ کالای واقعی از قبل seed شده، دسته‌بندی خودکار با کلیدواژه)، فیلتر دسته + جستجو + صفحه‌بندی سمت سرور، ویرایش مستقیم هر کالا (مودال)، ورود/خروج، هشدار کسری/انقضا، درخواست کالا (برای همه نقش‌ها)
- **کارتخوان**: پشتیبانی چند دستگاه هم‌زمان (هرکدوم آی‌پی/تنظیمات جدا)
- **حضور و غیاب**: ورود/خروج خودکار، ناهار/استراحت با سقف قابل‌تنظیم، سهمیه مرخصی per-user، لاگ کامل
- **وضعیت من و همکاران**: ۱۰۰٪ خودکار از داده واقعی حضور
- **پیام‌های داخلی**: چت کامل با تاریخچه، حذف، خوانده‌شده
- **پرسنل و دسترسی‌ها**: افزودن کاربر از داخل پلاگین، چندنقشی، انتخاب نقش هنگام ورود
- **تنظیمات**: عمومی، امکانات، کارتخوان (چنددستگاهی)، پیامک (ترز)، لاگ پیامک، مالی، دسترسی‌ها
- **دستیار پلاگین**: `dental-booking` — نوبت‌دهی آنلاین، وصل به برنامه ماهانه پزشک

## ۸. الگوی «داده اولیه seed» — برای هر لیست بزرگ (کاتالوگ، انبار و...)

وقتی یه لیست بزرگ (چندصدتایی) باید توی همه‌ی نصب‌ها موجود باشه:
1. داده رو به یه فایل PHP جدا تبدیل کن (مثلاً `class-inventory-seed-data.php`) — یه متد استاتیک که آرایه برمی‌گردونه. این فایل جزو کد پلاگینه، همیشه با کپی‌کردن پلاگین میاد.
2. یه دکمه‌ی «ورود دسته‌جمعی» بساز که این آرایه رو می‌خونه و INSERT می‌کنه — با چک تکراری (بر اساس نام) که چندبار زدن مشکلی نسازه.
3. **نکته:** خودِ داده (فایل PHP) با کد میاد؛ ولی روی هر سرور جدید، چون دیتابیس جداست، باید یه‌بار دستی دکمه زده بشه.

برای جدول‌های بزرگ (۵۰۰+ ردیف)، همیشه **فیلتر و صفحه‌بندی سمت سرور** بساز (`get_items_paged()` با `LIMIT`/`OFFSET` توی SQL)، نه رندر همه‌ی ردیف‌ها با فیلتر جاوااسکریپتی — کندی و سنگینی صفحه رو زیاد می‌کنه.
